# AI Evaluation Engine

## Контракт и границы

`app.ai.evaluator.LLMEvaluator` реализует существующий `AIEvaluator.evaluate(EvaluationContext) -> StructuredEvaluation`. Контекст содержит `ConversationDetail` (исходные текст, роли, timestamps, внутренние message IDs) и неизменяемый `VersionRead`. Модель не вычисляет итоговый балл. Orchestrator передаёт `EvaluationSubmission(source="ai")` в `EvaluationService.create()`, который повторно проверяет evidence и вызывает неизменённый Decimal Scoring Engine.

Публичный `POST /api/evaluations` по-прежнему принимает только manual/test. AI запускается только через job API, не принимает готовых ответов или произвольных URL от клиента.

## Провайдеры

- `OllamaProvider`: асинхронный HTTPX к native `/api/chat`, `stream=false`, `think=false`, `format` с JSON Schema. У base URL допускается суффикс `/v1`, который адаптер снимает для native API.
- `OpenAICompatibleProvider`: `/chat/completions`, `response_format=json_schema`, JSON object fallback в режиме auto при HTTP 400/422. Совместимость проверяется mock transport; конкретный облачный/vLLM deployment надо проверить отдельно.
- Оба реализуют `LLMProvider.generate_structured(messages, response_schema) -> Generation`. Сетевые timeout, connection, rate limit, HTTP, отсутствующая модель и невалидный ответ имеют отдельные безопасные коды ошибок.

По умолчанию разрешены только loopback-адреса. Redirect и proxy environment отключены. `LLM_ALLOW_REMOTE=true` — явная настройка deployment, которую нельзя менять через публичный API. Перед отправкой реальных диалогов внешнему провайдеру требуется отдельное разрешение владельца данных. API key хранится как SecretStr и не попадает в metadata.

В установленном Ollama 0.13.5 обнаружено ограничение llama.cpp grammar: `maxLength=10000` из исходной DTO вызывает HTTP 500. Адаптер удаляет из transport schema большие ограничения длины строк и maxItems, сохраняя minLength=1, типы, required, enum и additionalProperties. **Исходная Pydantic-схема не меняется и полностью проверяется после ответа.** Constrained decoding помогает структуре, но не гарантирует корректность аргументов или evidence.

Официальные контракты: [structured outputs](https://docs.ollama.com/capabilities/structured-outputs), [chat API](https://docs.ollama.com/api/chat), [thinking](https://docs.ollama.com/capabilities/thinking).

## Настройки

Полный набор находится в `backend/.env.example`; существующий `.env` не нужно заменять.

- Provider/model: `LLM_PROVIDER=ollama`, `LLM_BASE_URL=http://localhost:11434/v1`, `LLM_MODEL=qwen3:4b`, `LLM_API_KEY`, `LLM_ALLOW_REMOTE=false`.
- Generation: temperature 0, seed 42, think false, context 16384, max output 3072, keep_alive 10m. Эти значения задаются через соответствующие `LLM_*`. Контекст и лимит выхода должны соответствовать модели и серверу. OpenAI-compatible сервер управляет собственным размером контекста; приложение использует заданный размер для планирования prompt.
- HTTP: timeout 180 секунд, 2 дополнительных retries, базовая задержка 1 секунда с удвоением. `LLM_RESPONSE_MODE=auto|json_schema|json_object`.
- `AI_MAX_REPAIRS=2`: до трёх генераций при структурном/grounding/семантическом отклонении. Обратная связь содержит безопасный код ошибки и коды критериев, а не произвольный ответ модели.
- `AI_SEMANTIC_REVIEW=true`: дополнительный аудит результата. Отключение уменьшает надёжность и не рекомендуется для DEV/приёмки.
- `AI_EXPLANATION_LANGUAGE=conversation|RU|KZ|EN`: исходный транскрипт не переводится.
- `AI_CHUNK_OVERLAP=2`, `AI_MAX_CHUNKS=64`: пределы обработки длинного контекста.

Jobs закрепляют provider, model, prompt version и inference settings при постановке. Endpoint/секрет worker берёт из окружения; они не копируются в БД. При смене deployment необходимо остановить worker и проверить очередь до отправки данных на новый endpoint. Изменения prompts в коде требуют осознанного перезапуска worker; metadata фиксирует версию реализации, использованную фактически.

## Dynamic Prompt Engine

В каждый запрос включаются все поля выбранных критериев: код, заголовок, описание, секция, тип, вес, allowed_values, max_score, scale_labels, allow_na, na_condition. Код evaluator не ветвится по номерам 01–08. Новая версия и дополнительные критерии автоматически меняют prompt/schema; веса считает только Scoring Engine.

Реальный LLM system message содержит правила приложения. Транскрипт сериализуется JSON-данными в user message. Даже реплика с `speaker=system` остаётся обычными данными. Инструкции внутри диалога не могут менять системный prompt, DTO или расчёт. Детерминированная изоляция и тесты уменьшают риск prompt injection; абсолютной семантической устойчивости малой модели не обещается.

## Grounding и семантика

1. JSON parser отклоняет дублирующиеся ключи, NaN, не-объект и обрезанный ответ; Decimal сохраняется.
2. Pydantic проверяет DTO. Scoring Engine проверяет полноту критериев, дубли, неизвестные коды, шкалы и N/A.
3. Каждому AI-результату нужны evidence. Для yes нужна quote; для положительной шкалы — quote/range. Отсутствие действия имеет ограниченный диапазон. Quote проверяется как точная подстрока конкретной реплики, без «исправления» модели по ближайшему совпадению.
4. Проверяются message IDs, принадлежность диалогу, порядок диапазона и покрытие. Финальный `EvaluationService` повторяет DB-проверки.
5. Семантический auditor одним дополнительным вызовом проверяет соответствие evidence критерию, роль, требуемый порядок действий, N/A, противоречия и пропущенные нарушения. Неподтверждённые финансовые факты требуют явного признания неопределённости; `diagnostics.needs_human_review` и `review_codes` доступны UI.

Самопроверка той же 4B-моделью не является независимой экспертной верификацией. Качество измеряется отдельно от JSON validity, см. [benchmark](ai-evaluation-quality.md). Ошибка проверки не сохраняется как успешная Evaluation.

## Длинные диалоги

Оценка размера — консервативная эвристика UTF-8 bytes/2 + overhead; это не точное число tokenizer tokens. Резервируются выход и место для semantic audit. Native adapter дополнительно отклоняет ответ при близком к границе prompt_eval_count, чтобы не считать возможное усечение успешным.

Если полный контекст не помещается:

1. Разбить весь диалог на последовательные окна с перекрытием, сохранив IDs. Ни одна реплика не отбрасывается.
2. Каждое окно возвращает точный список просмотренных IDs и наблюдения/evidence **по каждому критерию**. Отсутствие в одном окне не означает отсутствие во всём разговоре.
3. Проверить покрытие всех реплик и grounding каждого окна.
4. Для каждого критерия передать факты из **всех** окон, оригинальные реплики кандидатов и начало/конец диалога, включая первый/последний ответ оператора; затем проверить финальный ответ и семантику.
5. Если даже отдельная реплика/набор фактов не помещается, вернуть `context_limit`. Увеличить контекст или отправить человеку; скрытого обрезания нет.

Эта стратегия дороже обычного пути. Она сохраняет контекстные доказательства, но extraction малой моделью всё равно может пропустить смысл: полнота покрытия не равна гарантии экспертной полноты. Тесты отдельно проверяют 115 реплик, RU/KZ/EN, середину диалога и запрещённые ссылки вне окна.

## Голос и конфиденциальность

Оценивается только уже имеющийся транскрипт звонка. Аудио не скачивается и не отправляется модели; аудиоссылка исключена из prompt. Нет оценки интонации, дикции и неподтверждённых эмоций. В diagnostics добавляется `voice_transcript_only`. Чатовый чек-лист используется только для доступных текстовых аспектов.

Логи: IDs, длительность, токены, коды ошибок. Без prompts, raw responses, текстов диалогов, URL аудио, секретов. Приватные локальные результаты находятся в игнорируемой `backend/data/` и в SQLite.

## Затраты

Ollama не выставляет API-счёт; электроэнергия/оборудование не бесплатны. Для заданных пользователем тарифов:

- API estimate = input_tokens / 1 000 000 × input_rate + output_tokens / 1 000 000 × output_rate.
- GPU rental estimate = фактические секунды / 3600 × цена GPU-часа.

Для инфраструктуры с несколькими задачами нужно учитывать простой и совместное использование. Неизвестные token usage остаются null. Тарифы в проекте не зашиты и не выдаются за официальные цены. Время и токены нужно суммировать по всем попыткам, включая неудачные; таймаут не всегда позволяет узнать потреблённые удалённым сервером токены.


## Уточнения RunPod pipeline (prompt cqa-2.4)

- Все фактические запросы клиента оцениваются по выбранному checklist; модель не должна
  придумывать дополнительные вопросы и штрафовать одну лишь краткость ответа.
- Evidence JSON Schema связывает quote с конкретным message ID и enum дословных
  исходных фрагментов. Короткая реплика доступна целиком, длинная — перекрывающимися
  фрагментами до 1024 символов с сохранением конца. Полный transcript остаётся в prompt.
  Это constrained decoding, а не подмена ответа модели. EvidenceValidator повторно
  проверяет результат; смысл цитаты проверяет semantic audit. Для chunk схемы включены
  только IDs текущего окна. Range/absence требуют границ.
- Semantic audit сначала формирует rationale по условию и IDs, затем решение.
  При отклонении critique и предыдущий ответ передаются repair как недоверенные данные,
  отдельно от system instructions. Они не сохраняются в публичных diagnostics/logs.
- Исправления ограничены AI_MAX_REPAIRS. Неуспешный результат остаётся failed.
- Native Ollama 0.40.15 действительно выполнила такую JSON Schema на Qwen3:14b,
  включая звонок со 115 репликами. Это не гарантия правильности вывода:
  [измеренное качество](ai-evaluation-quality.md).

Production откат программных инструкций на cqa-2.4 выполнен по измерениям:
последующие инструкции ухудшили agreement. См. полный [quality report](ai-evaluation-quality.md).
Каждая попытка сохраняет фактическую prompt_version в diagnostics; после freeze код
и prompts не обновляют. Закреплённые версии пользовательского чек-листа неизменны.
