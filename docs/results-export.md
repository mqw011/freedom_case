# Сдача CQA: results.json, формат 1.0

Основание — `CQA_Student_Guide_Appendix_Results.pdf`, страницы 1–3,
SHA-256 `cf9e282fee6ee6fdc9ac0b857a513e21ff3010ef99db8e4d61df64f8c079f741`.
PDF задаёт формат, пример и правила, но не содержит отдельного машинного JSON Schema.
`backend/app/results/schema-1.0.json` — наша строгая схема JSON Schema 2020-12,
воспроизводящая эти правила. Дополнительные проверки арифметики, покрытия набора,
уникальности критериев и связи с БД выполняет Python-валидатор.

Команда — **hustlers**, настройка в `submission.toml`. Реальная модель берётся из
закреплённых AI jobs, несколько имён перечисляются через запятую. `mode=local`
означает Ollama на собственном GPU Pod. Для другого deployment режим нужно явно
сменить на `external_api` или `hybrid`; exporter не угадывает его по названию модели.
Если в наборе вообще нет jobs, имя берётся из конфигурации, а все строки имеют error:
это не утверждение о состоявшемся inference.

## Одна команда перед сдачей

Из корня репозитория на локальном CachyOS, с разблокированным SSH Agent и настроенным
GitHub-доступом:

```bash
uv run --directory backend submit-results --runpod --prod-group-id FBroker --require-prod-complete
```

`FBroker` — фактически импортированный организаторский контрольный набор из 10 чатов.
Команда создаёт свежий согласованный SQLite snapshot через SSH на существующем Pod,
переносит его по SCP, проверяет SHA-256, формирует оба JSON, проверяет их по той же БД,
коммитит только два файла и выполняет обычный push в `origin/main`. Затем сравнивает
`git ls-remote origin refs/heads/main` с локальным commit SHA. Успех —
`submitted: true`, одинаковые `commit_sha`/`remote_sha` и SHA-256 обоих файлов.

`--require-prod-complete` запрещает отправку, пока хотя бы один контрольный чат не
имеет валидной готовой оценки. Ошибки DEV при этом разрешены форматом организаторов.
Без этого флага сохраняются все 10 исходных ID, включая честные записи error.
`--require-complete` строже: требует готовности всех оценок обоих наборов.

Настройка SSH используется из локального игнорируемого файла
`backend/data/runpod-stage4.ssh_config`, alias `cqa-stage4`; приватные ключи не копируются
на сервер. Если агент заблокирован, локально выполните `ssh-add ~/.ssh/runpod_cqa`.
Снимок берётся из `/workspace/cqa/data/cqa.db`; временные копии удаляются после команды.
Оригинальная локальная `backend/data/cqa.db` не перезаписывается. Сайт, очередь и worker
продолжают работать. Эта команда не импортирует данные и не запускает inference.

Установка новых CLI entry points: `uv sync --directory backend --locked --python 3.12`.
Для другой инфраструктуры можно передать `--database /absolute/path/cqa.db` вместо
`--runpod`. Источник открывается read-only, SQLite Backup API учитывает WAL.

## Отдельные операции

```bash
# Свежий DEV с сервера: ровно 65 записей, включая ошибки.
uv run --directory backend export-dev --runpod

# Только настоящий контрольный набор: ровно 10 чатов.
uv run --directory backend export-prod --runpod --prod-group-id FBroker --require-complete

# Проверка против свежего снимка БД, включая исходные ID и номера реплик.
uv run --directory backend validate-results ../results/dev/results.json --kind dev --runpod
uv run --directory backend validate-results ../results/prod/results.json --kind prod --prod-group-id FBroker --runpod --require-complete

# Проверка файла без доступа к БД: НЕ подтверждает происхождение ID/evidence и свежесть.
uv run --directory backend validate-results ../results/prod/results.json --kind prod --structural-only
```

Пути без `--output` всегда относительно корня Git: `results/dev/results.json` и
`results/prod/results.json`. Повторный запуск полностью и атомарно заменяет файл
свежим экспортом; завершившиеся jobs автоматически заменяют прежние error-записи.
Нет append, дубликатов или заполнения отсутствующих результатов случайными баллами.

`submit-results` требует ветку main, пустой Git index и отсутствие посторонних
изменений. Сначала фиксируйте проверенные изменения кода отдельно. Если remote main
изменился, команда откажется от push: синхронизируйте историю без force и повторите.
При сбое push локальный results-коммит сохраняется; повторная команда безопасна.
Неопубликованные изменения кода команда сама не отправляет. Результаты из одной
команды всегда соответствуют одному снимку БД; более поздние решения/переоценки
требуют повторного экспорта.

## Точное соответствие полей

- `conversation_id`: исходный ID импорта, без переименования. Проверяется полный набор ID.
- `01 → contact`, `02 → discovery`, `03 → identification`, `04 → consultation`,
  `05 → empathy`, `06 → dialogue`, `07 → closure`, `08 → critical`.
- `yes/no` преобразуются в JSON boolean, `na` — в JSON null. N/A только у discovery,
  identification, consultation, closure. consultation: 0/5/10/15/20; dialogue: 0/4/7/10.
  Экспортируется исходная ступень: dialogue=7, а не взвешенные 10.5.
- Для `status=ok` ровно восемь критериев, каждый один раз, с непустым rationale.
- `evidence_turns`: `message_index + 1` по всему исходному транскрипту, включая client,
  operator, bot, system. quote даёт одну реплику, range/anchored absence — весь
  включительный диапазон, отсортированный без повторов. Internal message ID не
  экспортируется как номер реплики. Цитаты и принадлежность сообщений повторно
  проверяет существующий EvidenceValidator.
- `final_score`: сохранённый финальный балл Evaluation, числом JSON, без float-конверсии.
  Валидатор повторно проверяет его существующим Decimal Scoring Engine, с перераспределением
  N/A и ROUND_HALF_UP. Официальный пример — 85.38; проверочный пример проекта — 81.88.
- `critical_flag` равен boolean критерия critical и не обнуляет итог.
- `status=error`: исходный ID, пустой criteria, score=null, безопасная причина error.
  Нет пропусков, подмены нулём или выдуманной успешной оценки.

Выбирается **последний job для каждого диалога на выбранной версии**. По умолчанию —
активная версия исходного чек-листа; `--checklist-version ID` закрепляет явную версию.
Если новая переоценка ещё не завершилась, старая оценка не подставляется скрыто.
Готовый job обязан ссылаться на completed AI Evaluation того же диалога и версии.
Manual/test не выдаются за AI. После апелляции берутся current_answer, final_score,
critical flag и причина последнего пересмотра; исходная оценка в БД не меняется.
Evidence сохраняет исходные ссылки: в текущей модели решение апелляции не заменяет их.

Фиксированный официальный формат поддерживает только восемь официальных кодов,
типов, весов, шкал и N/A. Изменение формулировки допустимо; математически несовместимый
чек-лист отклоняется. Для отдельной проверки изменённых жюри правил нужна согласованная
с организаторами схема, а не молчаливое переименование критериев.

## Конфиденциальность и диагностика

Полные транскрипты, evidence excerpts, audio URLs, prompts, raw provider errors и
секреты не экспортируются. Rationale использует сохранённое обоснование; перед
публикацией из него удаляются дословные длинные фрагменты транскрипта, цитаты, URL,
email, телефоны и распространённые токены. Это детерминированное сокращение, не новая
LLM-оценка и не гарантия распознавания всех видов персональных данных. Для незнакомого
набора перед публичной сдачей нужен просмотр обоснований владельцем данных.
Ошибки валидатора содержат код/путь поля, без отклонённого текста.

Опциональный `--manifest backend/data/...` (путь относительно текущего каталога)
записывает приватные job/evaluation/version/revision IDs и SHA снимка. Manifest
обязан быть gitignored и вне results; он не нужен организаторам. SQLite, секреты,
приватные manifests и SSH-настройки исключены из Git.

## Проверки

`uv run --directory backend pytest tests/test_results.py` проверяет официальный
пример, Decimal, шкалы, N/A, все 65 записей, отсутствие подмены старой оценкой,
апелляции, 1-based evidence всех ролей, чужие/повреждённые ссылки, сохранность БД,
повторный экспорт, отсутствие выдуманного PROD и безопасные сообщения об ошибках.
Изолированный bare Git remote проверяет отправку обоих файлов, идемпотентность,
защиту пользовательских изменений, отказ при изменившемся remote, повтор после
ошибки push и точное совпадение удалённого SHA. Тесты не обращаются к DEV API или LLM.
